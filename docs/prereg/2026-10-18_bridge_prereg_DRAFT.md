## 0. 只回答什么
在 BATS 表 7 的同款配置下（Gemini 3 Flash preview、mini-swe-agent、SWE-bench Verified、k = 50），做一次**大效应筛查**，回答：
1. **R-a**：告知预算的收益 T（原生交付评分 S 下）是否达到预设的大效应筛查门槛？
2. **Q1**：交付规则交互 J = T − Δ_H = R₀ − R₁ 是否超过总收益 T 的一半？
3. **Q2**：在自动收取规则下（评分 H），告知是否仍有正的残余收益 Δ_H？
4. **R-c / R-d**（次要）：BATS 式策略段的额外作用；预算数字与说明本身的作用。

Q1 和 Q2 是两个独立的问题，**可以同时成立**（0 < Δ_H < 0.5T 时就是如此）；判读时两者分别给出，不按优先级藏掉其中一个。J 和 Δ_H 都是**具体交付政策之间的收益差**，不是自然中介比例，也不识别规划机制。"仍有残余收益"不等于"交付影响很小"。

只做 100 题、每臂每题 1 次，所以只能检出大效应（§5）。不写小效应的证据，也不写"不存在效应"。

## 4. 记录的量，以及失败与未知怎么处理

**每条轨迹记录**：S、H、W；终止原因；提交时的步数；调用数；各类 token 数；已定价的成本与临时预留；每一轮显示的预算数字与计数器读数；`response.model` 与原始 `modelVersion`；盲交标记。

**三个评分量**
- **S**（原生交付）：主动提交的补丁的判分；没提交为 0。
- **H**（自动收取）：提交了的轨迹取提交补丁的判分；没提交的轨迹取截止时工作区 F 的判分。构造上每条轨迹都有 S ≤ H。
- **W**（统一取截止工作区）：每条轨迹一律取停下那一刻工作区 F 的判分，包括主动提交的轨迹（提交那一刻的 F，按 F-v6 规则包含 patch.txt 和复现脚本）。W 与 S、H 没有大小约束。

**终止原因（互斥）**

| 代码 | 含义 | S | H | W |
|---|---|---|---|---|
| SUB_NONEMPTY | 在 k 内主动提交，补丁含非空白字符 | 判提交补丁 | = S | 判 F |
| SUB_EMPTY | 在 k 内主动提交，补丁为空或只含空白 | 0（显式空提交） | = S | 判 F |
| CAP_STEP_DIFF | 到达 50 次上限，工作区有 diff | 0 | 判 F | 判 F |
| CAP_STEP_NODIFF | 到达 50 次上限，工作区无 diff | 0 | 0 | 0 |
| CAP_COST | 先触发 $3 上限 | 0 | 判 F | 判 F |
| FORMAT_EXIT | mini 因格式错误退出（2.1.0 没有这条路径，预期为 0；一旦出现即作工程检查） | 0 | 判 F | 判 F |
| ENG_FAIL | 工程失败：API 重试用尽、容器失败、计数不一致、运行时异常、计价失败、资源中止 | 未知 | 未知 | 未知 |

只含空白的提交记为 SUB_EMPTY（S = 0）：它不改动任何文件，与空提交等价。d1 judge 对纯空白补丁会照常评测，多半因补丁打不上而记未知，所以这里在 bridge 一侧先按"显式空提交"处理。

**规则**
1. **重跑**：ENG_FAIL 的轨迹可以从头重跑 1 次，用新的 attempt id，并在账本里记录。第二次仍失败，S、H、W 都记为未知。资源中止不重跑。计价失败先暂停，作者处理后重跑，仍计入"至多 1 次重跑"。API 层的瞬时错误按 mini 的重试处理，不算 ENG_FAIL。
2. **F 提取失败**（F 不支持、快照无效或截止时有残留进程）：用到 F 的 H 和 W 记为未知，S 照常判定。
3. **judge 返回未知**（基础设施失败、不稳定、补丁打不上）：只把对应的那个裁决记为未知。
4. **分母固定**：始终是 100 题 × 各臂，不删任何轨迹，不只保留完整配对。每臂分别报告 S/H 未知率和 W 未知率。
5. **最不利填补**：
   - **(a) S、H**：在保持 S ≤ H 的前提下填补。只有 S 未知时，S 取 0 到 H 之间；只有 H 未知时，H 取 S 到 1 之间；两者都未知时，(S, H) 取 (0,0)、(0,1)、(1,1) 之一。
   - **(b) W**：W 没有序约束，未知的 W 在 {0, 1} 中自由取值。**不套用 S ≤ H**。
   - **已知的保守之处**：主动提交的轨迹在提交补丁判分未知时，S 与 H 实为同一个裁决，只能同为 0 或同为 1；但数据模型按"两者都未知"处理，可行集里多了不可能的 (0,1)。这只会让结论更保守，不会产生误报，本版不改。
   - 每条主张都在**对它自己最不利的**填补下判读，只有在那种填补下仍成立才算成立。跨口径稳健性要求 H 和 W 两条主张分别成立；两者分别取各自最不利的填补，这比联合填补更保守。
6. **未知率熔断（10%，已定）**：任何一臂的 S 或 H 未知率超过 10%，所有规则一律判"未定"，结论只出工程报告。同样的计算照算一遍，作为"熔断后的保守附表"附在报告里，**明确标为不是结论**，只供读者判断未知值的影响。W 的未知率超过 10%（BATS 或 Silent 臂）只让跨口径稳健性记为"未定"，不影响主判读。

**退化提交**：报告 SUB_EMPTY 的比例；另报**盲交率**。盲交率按命令文本的启发式判定，规则写死在 `bridge/outcome.py`：最后一个写类命令之后、提交命令之前，没有任何测试类命令。
- 写类命令：`sed -i`、重定向到文件（/dev/null 和 &N 除外）、tee、patch、git apply/checkout/restore/stash、mv、cp、rm、touch、Python 的写文件调用。
- 测试类命令：python、pytest、tox、nosetests、runtests.py。
- 提到 patch.txt 的命令不计（mini 的提交流程会把 diff 写到这里）。
- 这只是描述指标，**不进任何判读规则**。

**漂移检查**（只报告）：把 Silent 臂的 S，与同一批题在公开条目里截到 50 次后的结果（合成 A：resolved 且 api_calls ≤ 50）逐题对比，给出一致表。由 `analyze.py --public-entry` 生成。

## 5. 精度（推断与模拟）

### 5.1 两臂差值
每臂每题 1 次、100 题时，配对差值的标准误约为 √(q/100)，q 为两臂结论不一致的比例。q = 0.2 时标准误约 4.5pp，80% 功效下的最小可检效应约 12.5–13pp；q = 0.4 时约 17.7pp。两层权重不均，标准误只膨胀约 0.11%。这些只是两臂差值的精度，不是 Q1 的功效。

1. 在干跑中做工程检查，优先排查二进制补丁、后台进程和判分失败（§7.5）；
2. 必要时按 §9 预先声明桥接版的提取规则变体。

## 6. 预先写死的判读（候选阈值见状态总表）

### 6.1 记号、区间与检验结构
- T = Δ_S(BATS−Silent)；Δ_H = Δ_H(BATS−Silent)；J = T − Δ_H = R₀ − R₁，其中 R₀、R₁ 分别是 Silent 和 BATS-style 的补救率（H − S 的加权均值）。因为每条轨迹都有 S ≤ H，所以 R₁ ≥ 0，J ≤ R₀。
- **区间**：按层、按题配对的百分位 bootstrap，B = 10,000。同一批数据上的所有量都用同一组重抽样，以保留臂与臂之间的配对依赖。这样得到的是**保留配对依赖的边际区间**（每个量各自一个区间），**不是**同时覆盖多个量的联合区间。v2、v3 的"联合区间"说法有误，本版更正。
- **检验结构**：
  - **主检验**：R-a。
  - **条件主检验**：Q1 和 Q2，只在 R-a 达到门槛时判读（固定顺序）。两者是两条独立的主张，可以同时成立。两条都用双侧 97.5% 百分位区间（C5）。名义水平要写准：
    - Q1 可以报"过半"或"不到一半"，Q2 可以报"正"或"负"，两端都会用到，所以每问是双侧检验。
    - **每个方向**的名义错误率是单侧 1.25%，**每问**两个方向合计 2.5%；**两问四个方向**合计，Bonferroni 的名义上界是 **5%**，不是 2.5%。
    - 只有每问只报一个预先指定方向时，合计才是 2 × 1.25% = 2.5%；本设计不是这种情形。
    - 这些都是**名义**水平。百分位 bootstrap 在 n = 100 下的覆盖只是近似的，§5.3 的模拟显示边界处有偏差。模拟里的改善不是严格保证。
  - **次要检验**：R-c、R-d。各自单侧 2.5%，不做多重校正，结论里标为次要。
  - **只报告**：ΔW 跨口径稳健性、严格版、Number−Silent 的 Δ_H 和 Δ_W、反转与"有害"的描述、各差值的包络区间。它们都不进入 R-e。
- R-a、R-c、R-d 都另外要求点估计 ≥ 门槛，所以零效应下的族错误率在模拟里明显低于三者相加的上界（§5.3）。

### 6.2 R-a：大效应筛查（主检验）
| 结果 | 条件（各自最不利的填补） |
|---|---|
| 达到门槛（通过筛查判据） | T 的点估计 ≥ 10pp 且 L(T) > 0 |
| 低于门槛 | U(T) < 10pp |
| 未定 | 其余 |
"达到门槛"的意思是**通过了筛查判据**（点估计 ≥ 门槛且区间下限 > 0），**不能**据此说真实收益 ≥ 10pp，也不等于复现了 BATS 的 18.6pp。低于门槛不等于"没有效应"。

### 6.3 Q1：交付规则交互是否过半（条件主检验）
J − 0.5T = 0.5·Δ_S − Δ_H。
| 结果 | 条件 |
|---|---|
| 过半 | L(J − 0.5T) > 0，**且** Silent 臂补救事件 ≥ 5 条（在该填补下） |
| 不到一半 | Silent 补救事件 ≥ 5 条时：U(J − 0.5T) < 0。不足 5 条时（bootstrap 不可信）：用 J ≤ R₀ 作**充分条件**，即 U_exact(R₀) < 0.5·L(T)。为保持这条主张的名义水平，两个界平分单侧 α：U_exact 每层取 α_Q/8，L(T) 取单侧 α_Q/4 |
| 未定 | 其余 |
| 未评估 | R-a 未达到门槛 |
- U_exact(R₀)：每层用单侧 Clopper–Pearson 求上界，每层 α = 0.025（对两层做 Bonferroni，整体 0.05），再按层权重加总。零事件时每层为 1 − 0.025^(1/n)：60 题层 5.96%，40 题层 8.81%，加权 7.17%。v3 文本误写为 1 − 0.0125^(1/n)，代码一直是对的，本版改正文本。
- **"不到一半"不等于"交付影响很小"**。

**撤销 v3 的"很少"一档及其必要条件（理由）**：
- v3 的"很少"要求 U(J − 0.25T) < 0，**且** U_exact(R₀) < 0.25·L(T)。第二个条件是对 R₀ 设上界，而 J ≤ R₀ 只是上界关系。所以只要补救不稀少，这一档就整个失效，"R₀ 和 R₁ 都大、但两者之差 J 很小"的情形被排除在外。按 K3 包络，R₀ 约 25–45%，这个条件根本不可能满足。
- 这条本来是充分条件（J ≤ R₀，所以 R₀ 小就推出 J 小），被写成了必要条件（AND）。v4 只在 bootstrap 不可信的稀少事件情形下，把它当作充分条件使用。
- v3 审核的模拟中，"很少"在 96,000 次判读里一次都没有出现；即使只修可达性，0.25T 这个边际在 n = 100 下也几乎不可检验（J − 0.25T 的抽样标准差约 4–5pp）。
- 所以 v4 不是放宽阈值来提高检出率，而是换了问题：0.25T 的门槛整体删除，不放宽；Q1 的两档用同一个 0.5T，不新增阈值；Q2 回答的是另一个问题（残余收益的符号），用 0 作界，也不引入新阈值。

### 6.4 Q2：自动收取之后是否仍有正的残余收益（条件主检验）
| 结果 | 条件（各自最不利的填补） |
|---|---|
| 正 | L(Δ_H) > 0，且精确符号检验（不加权，看 H 不一致的配对题）单侧 p < 0.025 |
| 负 | U(Δ_H) < 0，且反方向的精确符号检验单侧 p < 0.025 |
| 未定 | 其余 |
| 未评估 | R-a 未达到门槛 |
- **符号检验门槛（v4 新增，C6；辅助性质）**：
  - **为什么加**：Q2 没有点估计门槛。H 不一致的配对题很少时，百分位 bootstrap 偏宽松，例如 4 对全部同向时，bootstrap 下界可能大于 0，而精确符号检验 p = 1/16。R-a、R-c、R-d 有 10pp 的点估计门槛，不加这层门槛。
  - **它是什么**：一个**额外的保守门槛**，与区间判据同时满足才算成立。
  - **它不是什么**：
    - 不是加权总体效应的精确检验。主效应按两层的总体权重计算，符号检验却把两层的不一致题不加权地合并计数。每题权重相近（4.8 与 5.275），但两层效应方向相反时，两者回答的问题不完全相同。
    - 不能修正 bootstrap 本身的覆盖误差。
  - **模拟中的影响**（§5.3）：在加权 Δ_H = 0 的情景里，它把误报降低约 0.3–0.5pp。在两层反向、加权 Δ_H = +5pp 的情景里，它把"正"的检出率从 13.5% 降到 7.5%。效应大时不影响检出（(ii) 中两者都是 95.2%）。
- **"负"的措辞**：一律写"在自动收取评分（H）下告知收益为负"，不单写"有害"。R-a 达到门槛而 Q2 为负时，属于**效果随评分规则反转**：原生交付评分下为正、自动收取评分下为负。两个方向都要报告，反转本身不排除后续研究。

### 6.5 跨产物口径的稳健性（只报告）
- **主比较**：Δ_W(BATS−Silent)。Number−Silent 的 Δ_W 和 Δ_H 另报。
- 只在 Q2 有确定方向时检查：用 W 按 §6.4 的同一判据（区间加符号检验，W 用 §4 规则 5(b) 的填补）判同一方向是否成立。
- 结果分三种：两种口径下都成立，记 both_products；只在 H 下成立，记 H_only；W 未知率超过 10%，记"未定"。
- **解释边界**：这只说明结论对"混合产物口径（H）还是统一工作区口径（W）"是否稳健，不是规划机制的证据，也排除不了停止时点的作用。它不影响 R-e。

### 6.6 严格版（只报告，低功效）
L(J − 0.8T) > 0，**且** Δ_H 的 95% 区间完全落在 [−5, +5]pp 之内（闭区间），各自取最不利的填补。只在 R-a 达到门槛时计算。v3 审核的模拟中，48 格全部为 0%，因为 Δ_H 区间的宽度约 15–30pp，远宽于 10pp 的窗口。**未达到严格版，不能解释为"不等效"或"不主要来自交付"。**

## 7. 预算、支出停止线、计价与资源中止

### 7.1 费用与干跑
| 方案 | 条数 | 点估计（公开轨迹逐次调用成本求和） | 加 50% 余量 |
|---|---|---|---|
| 四臂正式 | 400 | $111 | $166 |
| 干跑（5 题 × 4 臂） | 20 | 约 $6 | — |

- **干跑费用（v4 写明，推荐值 C9）**：干跑用单独的支出账本（`dev=true`），上限 $15；正式账本从 $0 开始。干跑支出计入作者批准的总预算，**不计入**正式的停止线。两本账互相不能混用，代码在启动时核对。
- 公开轨迹里单次调用的最高费用（$0.041），不能当作新运行成本的硬上界，只作参考。

### 7.2 支出停止线
从 API 返回的用量实时累计支出（含格式错误轮），临时预留也计入。到 $200（C8）就停止，按资源中止处理。
- **这是软件停止线，不保证实际账单绝不超出**。原因有三：每次请求之前才检查，所以最后一次请求可能越线；有的调用可能已经计费，但响应没能落盘，账本看不到；服务方的计费口径也可能与 litellm 的算法不同。
- 实际支出以 Google 账单为准，干跑和正式运行结束后都要对账。
- 未完成的槽位记为未知，分母仍是 100 题 × 4 臂。
- **不加钱换结论，也不改为只分析已完成的题**：停止时点由累计费用决定，而费用可能与题目难度和结果相关，按随机顺序运行也消除不了这种选择问题。
- 如果要缩小规模，只能在干跑之后、正式运行之前一次性决定。
- **资源中止后的报告方式**：报告中止原因、中止时的累计支出、每臂已完成数和未知率。未知率超过 10% 即熔断，只出工程报告并附保守附表；未超过则照常按 §6 判读，未完成的槽位按最不利方向填补。

### 7.3 计价保护（v4 新增；离线核查见 `docs/d1_bridge_litellm_pricing_check_2026-10-19.md`）
- **已离线核实的风险**（litellm 1.106.0）：
  - litellm 按 `response.model` 定价。版本串不在价目表里或缺少 usage 时，**静默返回 0**；mini 在成本 ≤ 0 时抛错，这条轨迹记为 ENG_FAIL。
  - 版本串带某些后缀时（如 `-0930`、`-001`、`-20261001`），litellm 会**静默按基础型号的价格**计费，不报任何错。
  - 旧代码在这两种情况下都会漏记或错记支出，并且在重跑一次之后继续下一槽。
- **规则**：每次响应都先对照价目登记表 `bridge/pricing_registry.json` 判定计价状态：
  - OK：`response.model` 已登记、usage 齐全，并且 litellm 的成本与按登记价算出的成本在 1% 内一致；
  - 其余为失败，分为 NO_USAGE、UNREGISTERED_VERSION、LITELLM_COST_FAILED、PRICE_MISMATCH 四种。
- **失败时**：
  1. 这次调用的成本记为未知（**不当作 0**），支出账本另记一笔临时预留，每次 $1，标为待对账。**$1 是临时记账预留，不是这次调用费用的上界**；实际费用以对账为准；
  2. 这条轨迹记为 ENG_FAIL（原因 PRICING_UNAVAILABLE）；
  3. 账本置为"计价暂停"，整批在下一槽之前停下，**不立即重跑，不继续花钱**；
  4. 作者核对 Google 账单和新版本串的价格后，才能清除暂停（`spend.py --clear --note ... --reconciled-usd X`，用账单金额替换临时预留）。之后该槽按规则 1 至多重跑 1 次。
- **登记**：正式运行前，作者要按 Google 价目页和干跑账单确认登记表（`confirmed_by_author: true`），否则正式批次和单条正式轨迹都拒绝启动；干跑可以在未确认的状态下运行。
  - 登记表不计入 bridge 代码身份。登记的价格由 bridge 交给 litellm（`register_model`），所以补登一个 litellm 不认识的新版本串时，只需改登记表这一个文件，冻结的公开配置和代码身份都不变，已完成的轨迹不会因身份变化而被重跑。
  - 登记表的 sha256 和内容记进每条轨迹。判读时核对：它只能增加新版本串，已登记版本的价格、容差和预留金额都不能改，所有正式轨迹都必须在已确认的登记表下运行。不符合时报告标 REGISTRY_INCONSISTENT。
- **不做的事**：不把 mini 的 `cost_tracking` 改成 `ignore_errors`（那样 $3 上限会失效），也不把未登记的版本串静默映射到任何价格。
- **本地对账（作者 2026-10-19 要求）**：支出账本另有一份只追加的流水，每次模型调用记一行，键为"尝试号:调用序号:响应 id"。批量开始时和每槽结束后，`spend.reconcile` 把输出目录下所有的 calls.json（含 attempts/ 里的旧尝试）与流水逐条核对：
  - 已落盘的调用有没有漏记；
  - 有没有重复记账；
  - 金额是否一致；
  - 有没有找不到调用记录的孤立记账；
  - 临时预留是否都已用账单金额结清；
  - 账本总额是否等于流水之和。
  发现任何差异，批量暂停（STOP_RECONCILE）。作者核对账单后，用 `spend.py --out OUT --clear --reconciled-usd X --note ...` 结清。
- **只能靠外部账单的部分**：响应没能写进 calls.json、但服务方可能已经计费的调用（例如 litellm 收到响应后、返回前失败）。这类调用要在干跑和正式运行结束后与 Google 账单对账才能发现。

### 7.4 连续工程失败熔断（工程规则）
连续 3 次尝试都是 ENG_FAIL（不含资源中止）时，整批暂停，等待检查（例如模型下线、密钥失效）。这样系统性故障不会在 400 个槽位上每个都耗掉一次重跑。
- 暂停时，连续失败段里的尝试写进 `streak_*.json`。
- 作者查明原因、修好之后，可以用 `batch.py --void-streak FILE --out OUT --note "原因与修复"` 把这些尝试作废：它们不再计入各自槽位的 2 次上限，被作废尝试产生的终态结果移到一边保留，不删除。这样系统性故障不会永久吃掉槽位。
- 只有 ENG_FAIL 的尝试会进入连续失败段，所以作废不会抹掉任何有效的科学结果。
- **评测阶段的异常**：agent 已经跑完、评测抛异常时，整批暂停；续跑时只补做评测，不重跑 agent，不多花钱，也不多计尝试。

## 9. 二进制补丁与后台进程：F-b1（C11；作者 2026-10-20 确认方案 A）
K3 的 G=1 未知题里，有 4 题是 sphinx 构建文档时产生的非 UTF-8 二进制文件被 F 收进补丁，官方评测工具接收不了；另有 2 题截止时有后台进程（一题是超时后仍在运行的 `pip install -e .`，一题是 agent 自己启动的开发服务器）。桥接实验同样会遇到这两类情况，而且它们集中在未提交的轨迹上，正是对 Q1、Q2 伤害最大的未知类型（§5.2）。
- **方案 A（推荐；作者转来的意见同意）**：主分析沿用 F-v6，不改语义；另外预先声明一个桥接版变体 **F-b1**，只作次要敏感性分析。**原快照（F-v6 的产物）必须原样保留**；F-b1 改变了提取规则和停止时的处理（终止残留进程），所以它的结果**不能写成"恢复了原始截止状态"**，只能写成"按 F-b1 规则提取的截止产物"。F-b1 有两点不同：一是从 F-v6 中去掉 t0 时不存在、~~git 判为二进制的~~新增文件 ⟦2026-10-20 实现时收窄并在封存前改正：只去掉**内容不是合法 UTF-8** 的新增文件。理由：查 K3 的 sphinx-10449，评测工具拒收的原因是一个被 git 当作文本、却含非 UTF-8 字节的文件（objects.inv）；git 已编成 ASCII binary patch 的二进制文件（png、pickle）评测工具能接受，去掉它们没有必要，反而多改动评分对象。收窄后对 F-v6 的改动更少⟧；二是截止时若有残留进程，先记录进程表，再终止全部非保活进程，等 2 秒后取快照。F-b1 只在 F-v6 不可评或快照无效时才额外评测。
- **方案 B（未采用）**：主分析直接采用 F-b1。未知率会更低，但评分对象变了，与 K2/K3 不再可比。
- **方案 C（未采用）**：不做变体，只靠干跑排查。
- ⟦2026-10-20 已实现（作者确认方案 A 之后）⟧：`bridge/snapshot.py`（`drop_new_non_utf8`、`fb1_product`、`DockerSnapshotter._kill_and_resnap`）、`run_one.py`（另存 `F_b1.patch`）、`evaluate.py`（只在 F-v6 不可用时评测 F-b1，记录 `H_b1`、`W_b1`；S 不受影响）、`analyze.py`（`F_b1_sensitivity` 一节，用 F-b1 的 H、W 重跑全部规则，只作报告）。
  - **规则的精确定义（F-b1-v1）**：
    1. F-v6 的快照总是先取，并原样保存；
    2. 只有 F-v6 因残留进程无效时，才执行容器内的 `kill -9 -1`（不动 PID 1 的保活进程），等 2 秒后重新提取；重取前后都没有残留进程才有效；
    3. 只去掉 t0 时不存在、内容又不是合法 UTF-8 的新增文件。git 已编码成 ASCII binary patch 的二进制文件保留，已有文件的修改一律保留。

    - 离线测试 `tests/test_fb1.py` 5/5，含 K3 真实补丁：sphinx-10449 的 F 只去掉了 `objects.inv`，过滤后是合法 UTF-8；
    - 台式机真实 Docker 检查 `tools/check_fb1_docker.py`：残留的 `sleep 600` 让 F-v6 被判无效并原样保存；F-b1 终止进程后，重取前后进程表都为空，并去掉了非 UTF-8 的新文件；
    - 用本地镜像评测 sphinx-10449 过滤后的补丁：2 个槽位都通过（原先"不可评"）。这只验证工具，**不改 K3 的判读**。
  - 报告里 F-b1 的结果只能写成"按 F-b1 规则提取的截止产物"，不能写成恢复了原始截止状态。
